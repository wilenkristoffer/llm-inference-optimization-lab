# Project summary

What eleven phases of measuring local LLM inference on one consumer AMD card
added up to. Every number here was measured on this machine (RX 7800 XT,
16 GB, gfx1101; Ryzen 5 5600X; Windows 11 + WSL2) and is taken from the
phase documents, which hold the method, the raw tables and the caveats.

---

## What to take away

1. **Pick the model first; it outweighs every serving setting.** On 60
   code-scored mail-triage agent episodes, qwen3.5:4b scores 82% and
   qwen2.5:14b 25%. No setting the lab measured moved accuracy by more than
   a few points. Re-pick when new models appear: `evaluate.py` scores a new
   tag on the same suites in about an hour (Phase 10).
2. **If the model is close, fine-tune it on scripted runs.** A one-hour
   LoRA took qwen3.5:4b from 82% to 100% on D, level with the 27B it was
   compared against (98%), with no loss on the other suites. Perfect runs
   generated by code trained a better adapter than the 27B teacher's runs
   (D' 59/60 vs 55/60), so no big teacher is needed. Try a better prompt
   first: it is free and got the base model from 67% to 82% on D'
   (Phase 11).
3. **Fit the model fully on the GPU.** Decode is memory bandwidth. Ten
   percent of the layers on the CPU halves decode, and a model that pages
   over PCIe on Windows runs ~10x slower per agent turn while Ollama
   reports "100% GPU" (Phase 7).
4. **Keep the prompt prefix stable.** A timestamp at the top of the system
   prompt costs the 14B 23x in time to first token (2,051 vs 90 ms), because
   the prefix cache only reuses an unchanged start (Phases 5, 9).
5. **Check what the runner did, not what the setting says.** Ollama forces
   one slot for some architectures whatever `NUM_PARALLEL` says, bundles
   draft models that kill batching, truncates an overflowing prompt to half
   the window without an error, and its `/v1` endpoint ignores penalty
   fields (Phases 2, 5, 9, 10).
6. **vLLM is the throughput runtime on this card, once tuned.** It batches
   to 2,052 tok/s at 32 requests on a 1.5B (3,056 with tuned GEMMs), within
   2% inside Docker, and serves qwen3.5 with a LoRA adapter unmerged. It
   costs WSL2, a ~50 s start and more setup (Phases 3, 8, 9, 11).

|---|---|---|---|
| 1 | What is a trustworthy baseline? | Decode 222 tok/s (1.5B) to 44 (14B); noise ~1-2% cv; `localhost` costs ~2 s per request on Windows (IPv6 fallback) | A 5,450 tok/s prefill figure (one token in 7.5 ms); "the 1.5B doesn't know what a KV cache is" (the prompt was ambiguous); the RAM is DDR4-3600, not 3200 |

| 5 | What do tokens, prefill, truncation and caching really cost? | Truncation is oldest-first and keeps ~num_ctx/2; warm prefix 6 ms vs cold 223 ms; Swedish costs 1.31x English in tokens | Phase 1's prefill rate "was the intercept speaking"; cross-runtime output is byte-identical at penalty 1.0 |

Ollama 0.40.12 no longer accepts `ADAPTER`; merge into the GGUF (undoing

## Decode is memory bandwidth (Phases 1, 3, 7)

Each generated token reads every weight once, so decode speed is bandwidth
divided by model size.

| qwen2.5 | weights | decode tok/s | effective GB/s | of 624 GB/s |
|---|---|---|---|---|
| 1.5b | 0.99 GB | 222 | 219 | 35% |
| 3b | 1.9 GB | 129 | 246 | 39% |
| 7b | 4.7 GB | 83 | 392 | 63% |
| 14b | 9.0 GB | 44 | 399 | 64% |

The 14B is 9.1x the weights but only 5.0x slower: small models leave the
GPU underused per token. At FP16, vLLM reaches 153 tok/s (472 GB/s, 76%)
against Ollama's 121 (375 GB/s, 60%).

**Measured ceilings:** VRAM read 602 GB/s (97% of spec), PCIe 28 GB/s,
FP16 60 TFLOPS (80%).

**Offload is harmonic.** 5 of 49 layers on the CPU halves decode
(52.8 -> 26.5 tok/s). A 32B (19.9 GB) on this 16 GB card pages over PCIe:
4 tok/s while Ollama reports "100% GPU", ~10x slower per agent turn than
the 14B (55.5 vs 5.5 s). ROCm on Windows reports ~2 GB more free VRAM than
exists, because the desktop holds it.

**ROCm vs Vulkan.** ROCm prefills 2.3-3.7x faster. Vulkan decodes the 1.5B
8% faster and uses 300-800 MB less VRAM.

## Batching (Phases 2, 3, 9)

Ollama queues by default (`NUM_PARALLEL=1`): aggregate stays at ~197 tok/s
at 1, 2, 4 and 8 concurrent requests. At `NUM_PARALLEL=4` it scales 1.75x
on the 1.5B and 1.90x on the 14B.

vLLM, Qwen2.5-1.5B FP16:

| concurrency | aggregate tok/s | per request tok/s |
|---|---|---|
| 1 | 151 | 152 |
| 4 | 556 | 145 |
| 5 | 695 | 144 |
| 6 | 438 | 74 |
| 8 | 570 | 72 |
| 16 | 1,091 | 69 |
| 32 | 2,052 | 66 |

The cliff at 6 is a kernel switch: ROCm's skinny-GEMM path covers 1-5
tokens per step (with `VLLM_ROCM_USE_SKINNY_GEMM=0`, batch 1 drops to 76
tok/s). Ollama overtakes at 8 (648 vs 570) until vLLM's larger batches
take over. CUDA graph padding adds a second trap: batch 5 padded to a
graph of 8 runs at 78 instead of 144 tok/s, so capture size 5 explicitly.
With tuned GEMMs (TunableOp) vLLM reaches 3,056 tok/s at 32 on the 1.5B,
and the 3B goes from 331 to 1,897 tok/s (5.7x); Ollama tops out at ~1,125.

## Quantization (Phase 6)

Token-level fidelity against full precision (top-1 agreement / KL):

| quant | Qwen2.5-3B | Qwen3.5-4B |
|---|---|---|
| Q8_0 | 98.7% / 0.002 | 99.3% / 0.003 |
| Q4_K_M | 93.3% / 0.058 | 94.7% / 0.030 |
| Q3_K_M | 75.0% / 0.677 | 89.4% / 0.108 |
| Q2_K | 0.7% / 4.83 (broken) | 66.0% / 0.885 |

A 60-question checkable test could not tell FP16 from Q4_K_M. "Never go
below Q4" is model-dependent: Q3_K_M is viable on the newer model. The
Q2_K collapse on the 3B was traced to `ffn_gate` at 2 bits.

## Context, KV cache and caching (Phases 1, 2, 5, 9)

- **Truncation is silent.** Ollama drops the oldest tokens, keeps roughly
  `num_ctx / 2` (not just the excess), keeps the system prompt, and returns
  no error. The model then answered a question about a planted code that
  had been cut, confidently and wrongly. Detect it with `prompt_eval_count`.
- **KV cache size:** ~28 KB per token on the 1.5B, so 32k context is
  ~917 MB. Ollama preallocates `num_ctx x NUM_PARALLEL`; it is what you
  declare that counts, not what you use. Idle slots held 854 MB (~40% of
  the footprint) in Phase 6.
- **KV quantization:** `q8_0` is safe (KL 0.001-0.006) and fits the 14B at
  32k in 12.1 GB. `q4_0` silently ruins qwen2.5:1.5b and 7b.
- **Prefix cache:** a warm prefix prefills in 6 ms vs 223 ms cold; a change
  at the start drops the hit rate to 2%. Ollama's RAM prompt cache brings
  back an evicted conversation in ~35-40 ms.

## Telemetry and measurement (Phases 1, 4, 7)

- WDDM's GPU counters show ~0% during inference; LibreHardwareMonitor shows
  100%. Read it over its HTTP server.
- `ollama ps` reports what was allocated, not what is resident, and its VRAM
  figure runs ~270-320 MB low.
- Within-session noise is ~1-2% cv; between sessions ~4%. Comparisons that
  matter are interleaved in one run.
- Greedy output is not reproducible across runtimes: two servers with the
  same weights differ on ~13 of 320 turns (near-tie tokens).

## Checklist for an app that runs on Ollama

Each item is something this lab measured going wrong.

**Model and sampling**
- Choose the model with `evaluate.py` on your own task, not by size.
  bonsai-2:27b for accuracy, gemma4:e4b for throughput, as of Phase 10.
- Pin `temperature` 0 and a seed. Set penalties explicitly: qwen3.5's
  Modelfile sets `presence_penalty 1.5`, and Ollama's `/v1` endpoint
  ignores penalty fields, so use the native API or a Modelfile.
- Set `think` explicitly. qwen3.5 thinks by default and can spend the whole
  token budget on hidden reasoning, returning an empty answer.

**Connection and server**
- Use `127.0.0.1`, not `localhost`, on Windows (~2 s per request saved).
- `NUM_PARALLEL` defaults to 1, so concurrent requests queue. Set it at
  least to your fan-out; extra slots cost only VRAM. Then check the log:
  Ollama 0.40.11 forces one slot for qwen3.5 whatever the setting says.
- Check for a bundled draft model (`ollama show`): nemotron's turns
  batching from x2.90 into x1.08.
- Batched decode can change answers: gemma4 at 4 slots flipped 4 of 8
  episodes.
- Stopping Ollama must also kill its `llama-server` child; an orphan held
  4.2 GB.

**Context**
- Set `num_ctx`: the default is 4,096 and most frameworks never change it.
- Never rely on server-side truncation. Trim client-side with a margin and
  compare `prompt_eval_count` with what you sent.
- JSON tool results cost more tokens per character than prose (2.4 vs 3.3
  characters per token), and Swedish costs 1.31x English.
- Put stable content first. No timestamps or session ids near the start of
  the prompt.

**Agent loop**
- Give the loop a termination condition in code. The user's agent looped
  because it had none, not because of truncation.
- On an unknown tool name, return an error listing the valid names. Treat
  an empty reply that used tokens as a dropped tool call: Ollama's parser
  drops calls with no `arguments` key silently.
- Always cap `num_predict`; HTTP 500 "token repeat limit reached" can mean
  the model looped.

**Hardware**
- Fit the whole model on the GPU, with ~2 GB left for the desktop on
  Windows. "100% GPU" in `ollama ps` is a placement claim, not a
  measurement.
- Q4_K_M is a sound default; check Q3 per model before using it.
- Ollama unloads a model after 5 minutes idle (`keep_alive`); the first
  request after that pays the load.

**When to fine-tune**
- When the best model that fits is close but not good enough, and a correct
  run can be described as rules. Generate the runs with code, train a rank
  4-16 LoRA for about an hour, merge it into the GGUF and serve it as a
  normal tag. Check it on held-out templates and on the other suites.

## Known gaps

- Kernel profiling: `rocprof` had to be stubbed out to run vLLM in WSL2.
- The scripted adapter (s373-r16) has not been through `evaluate.py`, so it
  is not on the leaderboard and not checked on suites A, B, C and E.
- vLLM with an adapter was checked for correctness, not speed.
- One seed per fine-tune configuration.
- `OLLAMA_GPU_OVERHEAD` as the fix for ROCm's free-VRAM overstatement is
  suggested but not tested.
